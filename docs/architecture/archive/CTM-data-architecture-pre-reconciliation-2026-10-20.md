# CTM data hierarchy and database architecture

Current business-policy authority: [CTM confirmed decisions](CTM-confirmed-decisions.md). This detailed working document retains original proposals and superseding decision notes; do not implement an older conflicting paragraph without reconciling it to that register.

Date: 2026-10-20. Status: complete architecture proposal for review; no database provisioned, migrations executed, or interface changed. Based on the current prototype and the decisions in this conversation. Policy choices explicitly marked proposed remain subject to approval.

## 1. Scope and evidence

CTM is a complete server application with an applicant portal and a private council portal. Both operate on one authoritative PostgreSQL database. Private files live outside the public web root. Supabase and Neon are excluded. Plenix design-system CDN will be the later presentation layer; existing styling, PatternFly experiments, preview instrumentation, and simulated persistence are not the production foundation.

The evidence inventory covers all 49 top-level HTML pages: 18 public pages and 31 admin pages (including two design/consolidation previews). It records 647 static controls, including buttons, not 647 database fields. Dynamic repeaters, script-defined records, and shared workflow/permission definitions were also inspected. See `prototype-inventory.md`, `prototype-inventory.json`, and `prototype-to-data-map.md`. The PatternFly spike is a UI experiment, not a third business portal.

Evidence precedence: explicit user decisions > current prototype behavior and fields > embedded historical audit. Prototype copy is evidence of intended functionality, not verified canonical or legal policy. Demonstration people, statistics, case numbers, and dates are fixtures, not migration data.

Current implementation scope includes tribunal intake, applicant records, private evidence, council operations, decisions, notifications, administration, and reporting. Marriage preparation is a future module. Existing Holy Crowning pages are inventoried and assigned a future boundary rather than silently added to the current build.

## 2. Confirmed business rules

1. Each person can participate in many historical cases, but never more than one open CTM case at once. Enforce across all applicant accounts and case-party roles, not merely the initiating applicant.
2. A and B share a case number, but each owns a separate application, answers, uploads, and recipient-specific communications. Neither can access the other's application records.
3. Authorized council members can review both parties and all council case materials. An investigating assignment controls work responsibility, not automatic exclusivity of council reading.
4. A's submitted petition normally creates the case. B must have an application, created by B or on B's behalf, before an administrator associates B with the existing case. Association must not create a second case.
5. Case number format is `YYYYMMDD-##`, based on the case's actual creation date.
6. Temporary applicant reference is initials + birth date `YYYYMMDD` + gender `M/F`, e.g. `JS19850314M`. It is internal and not exposed as an applicant-facing temporary identifier.
7. Once associated, the CTM applicant reference is case number + hyphen + temporary-reference component, e.g. `20261020-01-JS19850314M`.
8. These references belong to CTM. They are not ecosystem-wide person identities or authentication credentials.
9. Submission must feed directly into council review without retyping or email import. Submitted versions remain preserved; later amendments do not overwrite them.
10. PDFs, images, and videos must be supported in secure private storage. The current evidence fixtures also include MP3 audio; preserve audio as a supported evidence category.
11. Architecture precedes visuals. The marriage-management workflow is deferred.
12. One council/tribunal operates this CTM application. Its authorized council members may review all its cases and both parties' submissions. There is no multi-council tenancy requirement; individual action permissions and applicant isolation still apply.
13. PostgreSQL is the approved database. Initial hosting is a dedicated CTM VM on the user's own server. Deployment must remain portable to another VM, Azure, or AWS without requiring a particular cloud database or storage provider.
14. Uploaded attachments require a system-assigned filename containing the case number, the subject applicant's identifier component, the document-type code and validated extension. Use the full case-specific CTM applicant reference (which already includes the case number) followed by the code: `20261020-01-JS19850314M-MC.pdf`. Confirmed codes: `MC` for church marriage certificate and `CMC` for civil marriage certificate. This supersedes the earlier case-only filename examples and the proposed A/B labels. The selected document category determines the code; ownership comes from the authenticated application/participation, not a client-supplied filename. For staff uploads on behalf of an applicant, use the subject applicant's reference and record the staff uploader separately. Preserve the original uploaded filename privately for provenance; use opaque private storage keys independently of the presented/download filename. Draft uploads before case creation receive the case-based filename on association, with no need to relocate their bytes. Confirmed attachment format: `[case number]-[applicant identifier component]-[document code]-[sequence].[extension]`, for example `20261020-01-JS19850314M-MC-01.pdf` and `20261020-01-JS19850314M-MC-02.pdf`. Sequence distinguishes separate attachments within the same case participation and document category; allocate atomically and never reuse a committed sequence. The sequence is not a revision number. Replacement uploads create a new immutable version of the same attachment and preserve all previous copies. Show the latest accepted version by default; authorized council members can view version history. Pending or rejected replacement uploads do not displace the latest accepted copy. The attachment sequence stays unchanged across versions. Attachment version history is council-only. Applicants can access only the latest accepted version of their own attachments; older versions remain inaccessible to them even through previously obtained version IDs or copied download/preview URLs. Submitted snapshots continue to pin the exact original file versions for council evidence, but applicant-facing submission views must not expose historical attachment versions. Council-only case-wide artifacts use the confirmed case-number/document-code/sequence format without an applicant ID. Version suffix naming remains to be settled; filenames never authorize access.

## Attachment acceptance decision

Confirmed: uploads require no council/staff acceptance or approval. Each successfully completed upload becomes the current attachment version automatically after automated file-security validation. In this document, "accepted" refers only to a completed upload that passed automated technical checks, never a council decision on readability, correctness, authenticity, evidentiary weight or relevance. Council review may record observations or request a replacement without an acceptance gate.

Authorization, transfer integrity, configured size/type limits and malware checks remain technical safeguards. A quarantined, malicious or failed upload is not served and does not displace the prior current version. This does not require council approval. The default displayed version is the latest successfully completed, technically safe upload. Applicants see only that version of their own attachments; previous versions remain preserved and accessible only to authorized council members.

## Post-submission attachment decision

Confirmed: after application submission and while the case remains open, applicants may upload additional attachments and corrected copies of their own attachments. No council request or approval is required. Additional documents receive a new attachment sequence; a corrected copy creates a new immutable version of its existing logical attachment. Preserve every submission and all previous file versions with uploader, subject applicant, server timestamp, source application/case, checksum and replacement relationship. The original signed application snapshot remains unchanged; later uploads are recorded as subsequent attachment submissions linked to the same application and case.

Applicants continue to see only the latest completed, technically safe version of each of their own attachments. Authorized council members can inspect the complete submission and version history. Upload authorization and finalization must check that the case is still open, including uploads started before closure. Post-submission answer corrections are also permitted while the case is open, through preserved revisions and field-change history; the original signed questionnaire is never overwritten. Applicant uploads after closure are governed by the closed-case and separate appeal-intake decision below.

## Closed-case, appeals and application fee decisions

Confirmed: when a case closes, ordinary applicant uploads and replacements are blocked. They resume only after an authorized council reopening, subject to the one-open-case-per-person guard. Applicants may nevertheless submit an appeal containing a petition and evidence/proof, accompanied by a fee. Appeal intake is a separate permission path: it accepts appeal-owned uploads while the original case stays closed. Merely drafting, paying for or submitting an appeal does not reopen the case or permit ordinary closed-case edits. Confirmed: the one-open-case-per-applicant rule applies to appeal eligibility as well. An applicant who already participates in another open case cannot submit an appeal concerning a closed case. No appeal-intake exception may bypass this rule. Check eligibility before checkout and again during finalization, with concurrency protection against a competing case opening; payment must not be taken for a known ineligible filing. Absolute invariant reaffirmed: there can never be two open cases for the same applicant. No administrator override, appeal workflow, reassignment, identity merge, concurrency race or reopening action may bypass it. An appeal belongs to its original case and cannot create a second case. Any transition that would open that case must atomically verify and acquire the applicable person_open_cases claims; if a participating applicant already has a different open case, opening/reopening is blocked. Confirmed appeal routing: after successful payment or an authorized waiver and formal submission, the appeal enters the council queue for approval or non-approval. Submission alone does not reopen the original case; it stays closed pending council review. Record queue status, reviewing actor, decision, reason and timestamps. A non-approved appeal preserves its petition, evidence and payment history with the original case closed. The effect of council approval or non-approval, reviewing-role grants and any later processing steps are explicitly deferred; approval is not defined as reopening.

Confirmed: each person filing a petition pays their own $250 online filing fee. If both parties file petitions concerning the same case, each pays $250; they share one case, not one fee. A party merely responding or being associated with the case without filing a petition does not incur a filing fee. This supersedes the earlier interpretation that the other party never pays when joining an existing case. An appeal carries its own $250 online fee payable by the person filing that appeal. Assess obligations by applicant and filing purpose, not merely by case or account creation. Successful payment or an explicitly authorized filing-specific fee waiver is required before formal submission of a fee-bearing petition or appeal. Applicants may save drafts and upload documents before payment. Payment is now in scope, superseding earlier fee-deferral statements. Currency is confirmed as USD for both petition and appeal fees: USD 250.00 per fee-bearing filing. Store the assessed currency explicitly and represent provider amounts as 25000 US cents where the provider requires integer minor units; never use floating-point amounts. Stripe Checkout is the preferred payment provider, provisionally selected by the user (not final, no account connected). Keep provider-specific integration behind a replaceable payment interface and retain provider-independent obligations, amounts, currency and filing links. Confirmed refund policy: the USD 250.00 petition or appeal filing fee is non-refundable once the filing is formally submitted. Accidental duplicate payments may be refunded; keep the valid payment allocated to the filing and link any duplicate charge and refund to that same obligation. Record the refund reason, amount, provider reference, requesting/authorizing actor and event history; do not delete payment records or mark the legitimate filing unpaid when refunding only its duplicate. Confirmed refund authority: either an authorized council application administrator or the council secretary may authorize an accidental duplicate-payment refund. Represent this as an explicit refund permission granted to those application roles; hosting/database administration alone does not confer it. Other council roles do not receive this permission automatically. Verify the duplicate and record authorization before requesting the provider refund; retain pending/succeeded/failed refund events without treating authorization alone as completed repayment. Confirmed fee-waiver authority: an authorized council application administrator or the council secretary may waive the USD 250.00 filing fee for a petition or appeal. Grant a distinct waive_filing_fee permission to these roles. An approved waiver satisfies that specific filing obligation and permits formal submission without a successful charge; it is an explicit exception to the standard payment-before-submission rule, not a successful payment. Record obligation, amount/currency waived, authorizer, reason and timestamp in immutable adjustment history. Do not create a provider charge or fake receipt for a waiver. Confirmed waiver process: applicants have no waiver-request option or waiver-request workflow in CTM. Waiver arrangements occur outside the applicant application. The authorized council application administrator or secretary records the approved waiver against the specific petition/appeal fee obligation through the private council portal, with authorizer, reason and timestamp. No applicant-submitted waiver request, public waiver form or automatic eligibility assessment is required. The final submission process recognizes the recorded waiver and skips checkout for that filing. Confirmed applicant flow: disclose the USD 250.00 filing fee before an applicant initiates a petition or appeal. Payment is the final step after the application, required documents and attestation are complete; do not offer payment for incomplete drafts or a separate pay-now/submit-later path. Start the final payment-and-submission operation against a frozen, fully validated submission candidate. After server verification of successful payment, automatically finalize that same filing idempotently; an authorized waiver uses the same final submission path without checkout. Preserve the fee notice/version shown. Do not create an ordinary paid-but-unsubmitted draft workflow. A successful external charge followed by a network interruption, case-link conflict or database failure remains a technical recovery condition: preserve the frozen filing and payment event, reconcile/retry finalization, prevent a second charge and alert staff if unresolved. This is not an applicant choice to defer submission. Waiver revocation, final provider approval/account onboarding and failed/disputed-payment policy remain explicit decisions. Do not infer payment-policy details from the dollar sign alone.

Unless the filing obligation has an authorized recorded waiver, submission must use server-verified successful payment matched to the correct applicant, filing, assessed amount and currency; a browser redirect or client-reported success is insufficient. Link the paid obligation to its immutable filing submission in a transaction, with idempotency and reconciliation so retries cannot charge twice or consume one payment for multiple filings. Payment alone does not create or reopen a case. If both parties are filing about the same marriage, routing to the existing shared case must be resolved before final submission; a second paid petition must not silently create a duplicate case or bypass the one-open-case rule.

Add appeal entities: `appeals` (case FK, appellant case-party FK, petition/submission FK, status, created/submitted timestamps), `appeal_submissions` (immutable petition and evidence manifest), and typed appeal attachment links retaining party ownership and version history. Confirmed appeal eligibility: an applicant may submit an appeal at any time after the case is closed, with no filing deadline or expiry measured from closure. Ordinary closed-case uploads remain blocked; appeal-owned petition/evidence uploads use the separate appeal-intake path. Appeals use the original case number without a separate public reference. Permitted rounds, review authority, disposition and any later case-state effects remain deferred to workflow discussion. A later evidence correction preserves the prior appeal submission rather than overwriting it. Applicants never see the other party's appeal materials.

Add payment entities: `fee_schedule_versions` (application/appeal purpose, amount, currency, effective interval), `fee_obligations` (subject application or appeal, payer/subject applicant, immutable assessed schedule and amount), `payment_attempts` (obligation, provider, provider transaction/session ID, amount/currency, state, idempotency key), `payment_events` (verified provider event ID, receipt time and processing outcome), and `payment_adjustments` (refund/dispute/waiver if policy allows, authority and reason). Use concrete application/appeal obligation FKs. Payment receipt and provider reconciliation must be auditable. Do not store raw card numbers or card security codes. Exact provider and verified payment integration are implementation decisions, not configured services.

## Case closure and appeal-intake clarification

Confirmed clarification: once a case is decided, that case is closed. Submitting an appeal creates an appeal submission linked to the closed original case and places it in the council queue; it does not open a case or reopen the original case. Appeal queue status must therefore be independent of case open/closed status and must not itself acquire a person_open_cases claim. An appeal is not a second case. Do not describe appeal submission as a reopening transaction.

The user has deferred the detailed processing procedures for both new cases and appeals until that workflow discussion. Reviewing authority, internal stages, the meaning/effects of appeal approval, and any subsequent case-state transitions are not decided here. Previously proposed automatic or approval-triggered reopening behavior is not an agreed requirement. Preserve the absolute one-open-case-per-applicant rule for operations that actually open a case, without using it to imply that appeal intake opens one. Whether a procedural deferral constitutes a final case decision will be settled in the workflow discussion.

Confirmed: while the case is open, applicants may correct answers in their own submitted application. Preserve the original submission and every committed change; never overwrite the original signed snapshot. Authorized council members can inspect the complete history. Once a case closes, applicant questionnaire edits are blocked; an appeal submission does not lift that restriction.

Each committed correction records application UUID, stable semantic field code, repeat-instance UUID where applicable, old and new answer state/value, changed_by actor, subject applicant, server timestamp, revision/submission lineage and chronological sequence. Preserve added and removed repeating entries, including their individual fields; deleting an entry must not erase its history. Draft typing/autosave before initial submission is not automatically a formally committed correction. Recheck the open-case state at commit and use optimistic concurrency to prevent a stale edit from silently replacing a later correction. Administrator/secretary corrections on behalf of an applicant are confirmed as permitted while the case is open; attribute each change to the actual staff actor and preserve the subject applicant separately.

The council form shows the latest committed answer and a history icon beside a changed field or its field area. Selecting the icon opens a modal with that field's original value and chronological changes, actor and server date/time. This is an interface requirement only; no modal or other visuals are implemented during architecture review. Query history by authorized application and stable field/repeat identifier, never HTML DOM IDs or current array positions. Exclude passwords, recovery secrets and payment credentials from questionnaire history. Confirmed answer-history access: applicants may view the history of their own questionnaire answers, and authorized council members may view both parties' histories. The changed-field history icon and modal are available in each permitted view. "Everyone" does not confer cross-applicant access: neither applicant may see the other's answers or history. Applicant-facing history shows only authorized answer changes and safe actor attribution; internal staff notes and sensitive administrative metadata remain private. This changes questionnaire-answer history access only; attachment-version history remains council-only under the separately confirmed rule.

Map corrections to `application_amendments` and immutable `application_revisions`; add `application_field_changes` as append-only rows linked to the amendment/revision. The source revision and normalized answers are authoritative; the field-change projection must be written in the same transaction or derived deterministically so it cannot disagree with them. Keep the original attestation tied to the original submission; it must not be presented as a signature over later corrected answers. Confirmed: no correction reason is requested or required. Preserve the previous and new values, the actual changing actor and the server timestamp for every committed correction. Confirmed: applicants do not re-sign or re-attest after correcting submitted answers. Saved corrections are sufficient while the case is open, provided every committed change preserves its previous/new values, actual actor and server timestamp. Keep the original declaration/signature bound to the original submission; display later answers as recorded corrections, not as retroactively covered by that signature. Confirmed: only the assigned council member and the council secretary receive notifications when an applicant commits an answer correction or uploads a new attachment or corrected attachment version. Other members, the presiding member and administrators are not included solely by role. If the assigned member is also the secretary, deduplicate per account/channel. Before a case has an assigned member, notify the secretary only. Notification routing does not reduce authorized council members' ability to review case records. Record the event transactionally with the committed correction or finalized technically safe upload, and dispatch through the outbox with idempotent delivery. Do not notify on unsaved keystrokes, interrupted uploads or rejected/quarantined bytes. Notifications link to the authorized case/application and relevant change; do not include sensitive answer values, DOB-bearing references or file contents in external messages. Applicant A never receives notifications about Applicant B's changes, or vice versa. Confirmed channels: both in-portal notifications and email for council notifications of applicant answer corrections and new/corrected attachments. Track each recipient and channel independently, including portal read state and email delivery attempts. Email contains only a minimal notice and authenticated link; sensitive answers, attachments and DOB-bearing applicant references remain in the portal. Confirmed email grouping: combine applicant answer corrections and new/corrected attachment events from one editing session into a short email summary, rather than sending one email per saved change. Preserve each underlying event and full field/file history independently. Group by applicant participation, case and recipient; never mix parties' private updates into an applicant notification. Use persistent notification batches with included event IDs, delivery status and idempotency keys so worker retries do not duplicate a summary or drop later changes. Portal notifications remain available without waiting for email delivery. Confirmed timing: portal notifications are immediate after a committed change or finalized safe upload. Send the grouped email summary after 10 minutes without further changes in that applicant/case editing batch. Each subsequent qualifying change resets the inactivity deadline to its server commit time plus 10 minutes. Persist deadlines in background-job/notification-batch records so restarts do not lose them. Claim and close batches atomically; changes arriving after a batch is closed enter a new batch. Resolve active assigned-member/secretary access before sending and deduplicate recipients. No periodic maximum-delay digest has been requested; continuous changes continue to postpone the email until the 10-minute quiet interval.

## Permanent case retention

Confirmed: cases are never deleted. Retain the complete case record permanently, including original applications and attestations, every committed answer correction, all submitted attachment originals and prior versions, council records, decisions/decrees, associated appeals and their submissions, filing/payment/waiver/refund history and audit provenance. Closure and archival do not erase records or authorize disposal. Applicant post-closure access remains limited to the authorized decree; permanent retention does not restore access to the rest of the case file.

Remove case purge and case-retention expiry from the production functional scope; the prototype permanent-purge control must not be implemented. Runtime application roles, including administrator and secretary, have no delete-case or purge-case permission. Use restricted database privileges and referential constraints to prevent destructive cascades from accounts, staff memberships or other parent entities. Document backups, migrations and disaster recovery to preserve permanent records, not merely currently open cases. Infrastructure administrators remain technically privileged; operational controls and protected recovery copies are required rather than claiming deletion is physically impossible.

The permanent rule applies to case records and submitted evidence. Temporary interrupted-upload chunks, malware-quarantine material, reproducible preview caches and expiring operational sessions are separate technical artifacts; cleanup must never delete a retained submitted original, prior version or case history. Replace retention-disposition proposals elsewhere in this draft with this confirmed policy for all case records. Capacity planning and backup preservation must account for indefinite growth.

## Participating and absent spouses

Confirmed: CTM does not handle same-gender marriage situations. A case is not required to have two participating applicants: one spouse may file when the other has deserted or does not participate. Do not require an account, application, fee, signature or assigned applicant reference for an absent spouse simply to satisfy a two-party schema assumption. Known spouse/marriage information remains attributable to its source; absence from the application process does not mean the marriage had only one spouse.

## 3. Deployment approach and alternatives

Decree clarification: do not impose recipient-specific copies or automatic redaction as a blanket requirement. The user directs CTM to follow decree/outcome-specific rules already represented in the prototype. `admin-case-decree.html` defines dissolution with permission for applicant, respondent, both parties or conditional permission; nullity with granted or conditional permission; and procedural outcomes deferred, denied, withdrawn and reconciled. `admin-management.html` contains versioned/configurable outcome and communication templates. Store outcome code/version, per-party disposition, applicable template, issued artifact and explicitly authorized recipients separately. A party's permission-to-remarry disposition, a communication recipient and permission to download a decree are distinct data and must not be inferred from one another. Precise decree content, issuance and delivery rules belong to the deferred case/decree workflow discussion. The proposed generic recipient-specific/redacted-copy policy is not approved. Applicant isolation for questionnaires, evidence and internal findings remains unchanged.

Recommended: a modular server application, PostgreSQL, private file storage, and a background worker using the same application codebase. Internal module boundaries are not microservices. Server-side authorization mediates every portal request. No browser receives database credentials.

Alternative A: managed PostgreSQL and private object storage under an established infrastructure provider. Reduces database operational work but requires provider, region, contract, and access decisions.

Alternative B: an entirely self-managed server with PostgreSQL and encrypted local private file volumes. Provides direct operational control but puts patching, backup verification, disk capacity, and recovery on the operator. This is a valid initial deployment if off-server recovery copies exist.

Alternative C: separate databases for the two portals. Not recommended: application and council data would require reconciliation and could drift. Two portals do not imply two sources of truth. Isolation is based on person, case-party ownership, permissions, and database policy.

PostgreSQL and initial hosting on a dedicated CTM VM on the user's own server are approved. Choose a supported stable PostgreSQL release at implementation time. Server framework, guest operating system, identity library/provider, storage product, physical region and backup destination remain selection decisions, not installed dependencies. A single application may use separate web and worker processes and separate storage/database services on the same initial host. Keep host-specific paths, endpoints and secrets in deployment configuration; use a replaceable private-storage interface. Migration to another VM, Azure or AWS must cover database, private originals and derivatives, secrets, encryption keys, counters and recovery verification without a cloud-specific dependency.

## 4. Logical hierarchy and terminology

The following is a relational hierarchy, not a requirement to duplicate nested copies of every record.

- Ecosystem identity: Person; Account; verified account-person link; contact points and profile history.
- Organization: Diocese; Tribunal; Parish; clergy directory; staff memberships; roles and permissions.
- Marriage registry boundary: Marriage; marriage parties; ceremonies and certificate facts. CTM may create provisional registry records from assertions without implementing marriage preparation.
- CTM applicant: person-specific CTM profile; private draft applications; temporary reference history.
- CTM case: immutable case number; relevant marriage; participating people; role and CTM applicant reference per participation; lifecycle and assignment history.
- Party application: questionnaire version; saved revisions; submitted snapshots; person/spouse/family/marriage/separation assertions; narrative; uploads; declaration and signature.
- Council casework: reviewed facts and provenance; intake interviews; adult witnesses and clergy contacts; internal notes; follow-up requests; investigations and recommendations.
- Council proceedings: sessions; rosters and attendance; agenda entries; case hearings; hearing notes and recordings; decisions and votes; per-party remarriage permissions and conditions; decrees and issuance.
- Communications: per-party secure threads; external correspondence logs; notifications and delivery attempts.
- Supporting controls: private file versions and derivatives; audit events; reference catalogs; exports; retention holds; outbox jobs; backup verification records.

Person is not Account. A spouse mentioned by A is not automatically a verified applicant or account holder. An application is not a case. An initiating applicant and respondent are case roles; both can be applicants in the user portal. Documents and evidence use the same storage subsystem but retain distinct business classifications. A decision is not the same thing as a decree or case closure.

## 5. Identity and identifier allocation

All entity primary keys are opaque UUIDs generated independently of display references. References containing DOB or initials never appear in object keys, public search, email subjects, unauthenticated links, or authorization checks.

### Case numbering

Store `id`, `tribunal_id`, `created_at` (UTC instant), `creation_local_date`, `numbering_timezone`, `daily_sequence`, and `case_number`. Confirmed numbering timezone: America/Los_Angeles, including its daylight-saving rules, regardless of applicant location, browser timezone or server host timezone. Derive the creation date and daily counter reset from the authoritative server event timestamp in this timezone; do not hardcode a fixed UTC offset. Preserve the captured date/timezone even if configuration changes later. Calendar date is not derived from the applicant browser's clock.

Maintain one counter row per creation date in the CTM deployment. Allocate its next value by atomic upsert/row lock in the case-creation transaction. Enforce unique `case_number` and unique `(creation_local_date, daily_sequence)`. Format the date without punctuation and sequence with two digits, beginning 01. Never use `COUNT(*) + 1`. Persist and return the same result on an idempotent retry.

Confirmed: the two-digit daily sequence and maximum of 99 newly created cases per day are sufficient. Retain exact format YYYYMMDD-## with daily values 01 through 99. On exhaustion, refuse further new-case allocation for that date, preserve the draft and alert operations; never silently widen, wrap, reuse or invent a date. Recheck capacity before final payment checkout and protect allocation/finalization against races; any external-payment completion conflict uses the recorded reconciliation procedure rather than double charging or generating an invalid number. Date changes or counter rollback after disaster recovery must not cause reissuance of a previously communicated number. Deletion never recycles a number.

Confirmed organizational scope: one council/tribunal and one case-numbering namespace. Retain the tribunal record for organizational settings, staff memberships, and historical attribution; do not build multi-tenant council isolation or cross-council access. Authorized council members may review all this tribunal's cases. Any future independent tribunal integration requires a separate scope and namespace decision.

### Applicant references

Confirmed initials: first-name initial plus last-name initial only; exclude all middle names. For example, John Michael Smith uses JS. Proposed normalization uppercases the initials and stores the exact normalized component. English-spelled first and last names are confirmed as the source of initials, even in Arabic applications; do not auto-transliterate. Exceptional single-name handling remains unspecified. Assigned IDs remain unchanged after corrections under the confirmed identity policy. Do not substitute invented DOB or gender when missing. Internal draft records can exist before sufficient identity information is entered; assign the temporary reference only when its components are present.

The temporary reference is a non-unique internal label. The assigned reference is stored on `case_parties`, not on the global person or login. Confirmed male/female spouse scope means the gender component distinguishes the participating spouses within a case; no same-gender collision suffix is needed. Enforce uniqueness of an issued case-specific reference without generating unapproved suffixes; reject erroneous duplicate association for staff resolution. Opaque keys remain authoritative; never merge identities automatically based on reference components.

Confirmed: an assigned case-specific CTM applicant ID is permanent and unchanged by later corrections to name, DOB or gender. Record corrected details through attributed history without regenerating the issued reference or existing attachment filenames. Store the issued identifier component separately from mutable current person details; do not recompute it on reads or profile saves. This supersedes the earlier proposed superseding-label policy. A later case gets its own new case-specific reference, not a new ecosystem person. Retain original issuance provenance; the identifier is a historical label, not proof that its embedded details are current.

## 6. Relational dictionary and conventions

Notation: PK means UUID primary key unless stated; FK means a checked foreign key; `?` means nullable; `[]` means multiple child rows. Fields below are semantic schema definitions, not executable migrations. Every mutable business row also has `created_at`, `created_by`, `updated_at`, `updated_by`, and integer `row_version`. Immutable records have creation/recording metadata and supersession links instead of general edit/delete. Cross-case and cross-party relationships must be enforced through composite unique keys/FKs, not just application validation.

Use PostgreSQL `date` for DOB and civil dates, `timestamptz` for events, `text` with appropriate maximum lengths for strings, `boolean` only for truly binary known answers, `bigint` for file bytes, and `numeric` plus ISO currency for money. Unknown, not asked, not applicable, and declined are distinct answer states. Never turn absent answers into false. Store phones in normalized international form plus original input; addresses support international formats. Age, marriage duration, counts, and dashboards are derived, with an explicit as-of date where relevant.

## 7. Application-to-council data flow

### A creates the case

1. Verify account ownership. Create/link a verified person and private CTM application. Do not require a case number to save a draft.
2. Validate and save structured answers with revision/optimistic-lock checks. Assign internal temporary reference after name, DOB, and gender are sufficiently known.
3. Complete safe upload scanning and the applicable document requirements. Capture declaration version, acceptance, and signature against the exact submission content.
4. In one transaction, lock the person; validate no existing open case; allocate case number; create marriage/provisional relation if necessary, case, A participation, open-case claim, immutable submission, attestation, audit, and outbox event. Repeated requests use the same idempotency key.
5. Council review reads the committed submission and private assets directly. Email is notification, never the mechanism that transfers the record to council.

### B joins the existing case

1. B creates an independent private application, or authorized staff creates one on B's behalf. Capture staff actor separately from subject applicant. A cannot create B's authenticated account or attest as B.
2. Admin verifies the identity and intended existing case, reviews competing open-case claims, and associates B's application with that case. B's submitted application must not automatically create another case while awaiting this association. Application routing modes: initiating petition versus response awaiting association; response applications cannot self-assign by guessing a case number.
3. In a transaction, lock B, acquire B's open-case claim for this existing case, create or verify B participation, assign B's case-specific reference, log association, and queue B's invitation/notification. A case number alone is never sufficient authority.
4. If B was previously represented only by A's spouse assertions, preserve those as A-authored evidence. After verification, link the correct stable person without copying or exposing A's statements into B's portal.
5. B claims their account with a verified single-use invitation and can review their own application. Proposed rule: administrative case association can occur before B confirms a draft, but no staff entry counts as B's signature or submitted attestation. Confirmation policy remains for approval.

### Amendments and reviewed facts

Both parties keep independent original submissions. Council may compare contradictory facts and record a reviewed value with source links and rationale. Council edits never silently modify a signed application. Correcting personal data does not rewrite older case evidence or another person's assertions. Changes to A's spouse statement do not notify B of the contents or update B's profile automatically.

### Open-case rule under concurrency

`person_open_cases` is a narrow transactional guard: primary key on `person_id`, with participation FK verifying same person and case. An applicant can join the case they already occupy, but cannot acquire a different open-case claim. Creating/joining/reopening/closing/merging a case locks affected persons in deterministic UUID order and updates claims in the same transaction as case state. No direct runtime writes to these tables outside guarded operations. Triggers/privileged routines enforce that every verified applicant participation in an open case has exactly its matching claim and that no claim points to a closed case. FKs and unique keys alone do not enforce this lifecycle equivalence.

Confirmed: an applicant with an existing open case cannot start a new application draft for another case. Enforce this before draft creation, not just payment or submission, including when the open case was entered historically. Drafts do not themselves create open cases, but a new-draft creation transaction must lock/check the stable person against person_open_cases. New-case submission remains blocked while another is open. Association of a responding application with the same existing case is a separate workflow, not permission to create another-case draft; its details remain deferred. A still-unverified spouse assertion does not reserve someone else's identity; later verified association performs the guard. Identity duplicates must be reviewed and merged through an audited process; account uniqueness alone cannot guarantee person uniqueness. Reopening is blocked if either verified applicant already has another open case. Case closure releases all claims atomically. Historical records remain.

## 8. Workflow design

Keep three independent state machines rather than one ambiguous status column:

| Record | Proposed states | Meaning |
|---|---|---|
| Application | draft, awaiting_confirmation, submitted, amendment_requested, superseded, withdrawn | A private draft is not an open case |
| Case lifecycle | open, closed | The one-open-case invariant uses this field |
| Case stage | received, validation, awaiting_information, unassigned, investigation, hearing, council_review, decision_recorded, decree_preparation, notification, complete | Workflow labels/version are configurable; none alone releases the open-case claim |
| Council session | scheduled, in_progress, completed, cancelled | Attendance and minutes are tied to session history |
| Decree | draft, awaiting_approval, approved, issued, superseded | Issuance creates an immutable PDF |
| File version | uploading, quarantined, scanning, accepted, rejected, processing_failed, retained, disposed | Only accepted originals and approved safe derivatives are served |

Closing requires an authorized actor, reason, applicable decision/decree preconditions, and audit. A deferred decision keeps the case open. A granted decision does not necessarily release the open-case claim before actual closure. Archival is a storage/visibility attribute of a closed record; purge is a separate governed operation. Withdrawal requires its own recorded closure decision rather than deletion. Case public status is a small approved projection; it does not expose hearing notes, other-party events, vote counts, or internal recommendations.

## 9. Permission and disclosure architecture

Authentication identifies the actor. Authorization separately checks active membership, tribunal, action, record ownership, current status, and disclosure scope. Deny by default. Browser routes and hidden buttons are not security controls. A person appearing in a document is not the owner of that document; authorship/submitting party determines source ownership.

| Resource/action | Applicant A | Applicant B | Active council member | Secretary | Presiding |
|---|---|---|---|---|---|
| A private application/files/attestation | Own | Denied | Read | Read | Read |
| B private application/files/attestation | Denied | Own | Read | Read | Read |
| A/B draft editing | Own draft | Own draft | Only separately granted on-behalf action | On behalf with provenance | Only separately granted |
| Signed submission modification | No in-place edit | No in-place edit | No in-place edit | Amendment only | Amendment only |
| Shared case number and approved own-party status | Own participation | Own participation | Read | Read | Read |
| Internal notes/intake/votes/recordings/recommendations | Denied | Denied | Read; permitted casework writes | Read/write by permission | Read/write by permission |
| Party-to-council thread | A thread only | B thread only | Read; write only if granted | Manage | Manage |
| Schedule hearings | No | No | No by prototype default | Yes | Yes |
| Draft decree | No | No | No by prototype default | Yes | Yes |
| Approve/issue decree | No | No | No | No | Yes |
| Manage staff | No | No | No | Yes by prototype default | Separate explicit grant |
| Export/purge or disclose records | No bulk export | No bulk export | Separate explicit grant | Separate explicit grant | Separate explicit grant |

Prototype permission defaults are starting proposals, not sufficient authority for every future operation. Preserve the explicit prototype distinction between reading all cases and managing particular operations. A hosting/system administrator has no automatic application-level tribunal role. Disabled staff lose sessions/access immediately but remain attributed in historical records. Clinical/confessional/clergy involvement does not confer portal access.

Applicant-facing queries are scoped by authenticated stable person + owning case participation, never by common `case_id` alone. Applicant projections must exclude nested other-party references, storage metadata, internal labels, internal emails, other-party counts, filenames, search hits, history events and autocomplete. Case-level records remain council-only unless exposed through a purpose-built sanitized own-party projection.

Submitted party documents remain available to their submitting applicant under the proposed own-record policy. Nothing uploaded by B becomes visible to A even if described as a joint marriage certificate. A can see their own independently supplied copy. Internal artifacts, including decrees containing both parties' sensitive data, are not automatically published. If applicants require outcomes/documents, prepare separately reviewed recipient-specific notices; a release cannot be used to bypass the confirmed isolation rule.

PostgreSQL row-level security is a second layer, backed by server authorization. Use a runtime database role that is not superuser, table owner, or BYPASSRLS; use FORCE ROW LEVEL SECURITY as appropriate. Separate migration ownership from runtime. Pass actor context transaction-locally from verified server session; never accept actor/role context from request JSON. Reset pooled connections; apply policies to reads and writes, child joins, jobs, views, and reporting. Use constrained functions for lifecycle/numbering and review SECURITY DEFINER search_path/permissions. RLS does not sanitize columns or artifacts; separate tables/projections are still necessary. Sources: [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## 10. Private PDFs, images, videos, and signatures

Recommended initial storage contract: private encrypted filesystem volume outside web root, behind an application storage interface. Object storage can replace the backend later without changing case/application ownership. The storage engine is not the permission engine. Originals have random opaque keys independent of case number, applicant reference or filename. Database rows hold names/metadata; file bytes do not normally live in PostgreSQL.

Upload flow: authorize owner and application state; establish size/quota and allowed category; stream or multipart-upload into quarantine; verify actual bytes, MIME/signature and limits; compute checksum; scan in isolated worker; reject unsafe files; accept clean original; generate sanitized previews/thumbnail/transcodes locally in constrained jobs; mark availability. Never trust extension, client MIME, filename, or a successful transfer alone. No downloadable original while scanning. DOCX appears in prototype summary uploads: support only with explicit category policy and safe processing, not arbitrary office/archive execution.

Video requires bounded resumable uploads, range streaming, storage capacity limits, duration/codec checks, processing timeouts, and private derivatives. PDFs require safe previews without executing active content; images require decoding limits and privacy-aware derivative metadata handling. Preserve original evidence bytes and their metadata; stripping metadata applies to derivatives. Signature images are private original files linked to attestations or approval, not reusable public profile images. OCR/transcripts are machine-derived unverified text until reviewed; never send to external AI/OCR services without an explicitly chosen approved processing arrangement.

Every download/preview/thumbnail/stream request rechecks actor ownership/permission and accepted state. For strict isolation, proxy authenticated delivery rather than long-lived bearer file URLs; copied URLs must not authorize another account. If signed storage URLs are introduced, document their bearer-access window and revocation limitations before adopting them. Set private/no-store cache policy for sensitive responses and do not route evidence through the public design-system CDN. Sandbox file rendering, sanitize display filenames, return safe content disposition, restrict browser content types, and authorize video range requests. Log access without logging document contents.

Track document categories separately: applicant photo, spouse photo supplied by applicant, government ID, church marriage certificate, civil marriage certificate, civil divorce decree, restraining order, party narrative, clergy statement, counseling report, witness statement, investigation report, hearing recording/transcript, correspondence, issued decree, and signature. A photograph is not a government-issued ID. Same bytes in two applications do not imply shared access; do not expose cross-owner deduplication results.

Database and file writes cannot form one filesystem transaction. Use staged upload records, immutable version IDs, a commit/finalization state, outbox jobs, and orphan cleanup with retention grace. Deletion must coordinate database disposition and file derivatives and honor holds. Sources: [OWASP file-upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

## 11. Security and server operation

- TLS at reverse proxy; PostgreSQL and private storage reachable only through restricted host/private-network paths. No public database port or public file directory. One host is an operational starting point, not high availability.
- Maintained authentication component with strong password hashing, verified email, expiring recovery and login throttling. Confirmed: two-factor authentication is not required for council accounts; remove the earlier mandatory-MFA proposal. Optional two-factor enrollment has not been requested and is not assumed. Invite staff without emailed passwords. Council inactivity timeout is disabled as confirmed; retain server-side revocation and current-role checks. Other session mechanics follow explicitly approved policy; role change/deactivation revokes affected sessions. Recovery is audited and uses expiring single-use verification tokens.
- Secure HttpOnly/SameSite session cookies; CSRF protection for state changes; parameterized SQL; server validation; output escaping; sanitization of rich-text decree/intake/template content; restrictive content security policy. Remove prototype preview bridge/message listeners from production. Plenix CDN version/integrity/availability strategy must be verified later without sending case data to it.
- Disk/object and backup encryption, separately controlled keys, restricted administrator access, key rotation/recovery procedures. DOB-bearing references receive the same protection as DOB fields. Hashes of predictable DOB references are not anonymization.
- Credentials from restricted secrets management, not application source, browser storage, logs, or exported settings. Separate production/staging identities and use synthetic data in development.
- Append-only application audit with restricted database privileges and protected external retention for tamper evidence. Database operators can otherwise alter local records; do not claim immutable against all administrators. Capture reads/downloads/exports/role changes/associations/decisions and denied access. Avoid full narrative bodies in audit/search/error logs.
- Notifications contain minimal notices and authenticated links; do not email evidence, DOB references, other-party information or shared reply-all lists. Store delivery attempts and recipient snapshots. Retry without duplicate sends using outbox/idempotency keys. Unverified or unsafe contact addresses cannot receive sensitive notices.
- Regular vulnerability/patch maintenance, access reviews, monitored scan/job failures, backup alerts, storage/counter exhaustion, and a documented incident response procedure. No security guarantee follows merely from selecting PostgreSQL.

## 12. Indexes, integrity, search and reporting

Required unique keys include case number; daily counter date; case sequence per date; `(case_id, person_id)`; person open-case claim; applicant person per tribunal; current lead assignment via partial unique index; vote per decision/member; revision number per parent; session agenda position where applicable; active normalized account login under chosen identity rules; idempotency key per actor/operation; and storage object key.

Index all frequently joined FK columns; case list filters `(tribunal_id, lifecycle, stage, created_at)`; party case history `(person_id, linked_at)`; owner drafts `(ctm_applicant_id, status, updated_at)`; hearings `(session_id, status)`; evidence `(case_id, category, created_at)`; correspondence `(case_id, occurred_at)`; audit `(case_id, recorded_at)` and actor/time; job state/due time; files scan state/created time. Use partial indexes for single active lead and pending work when justified. [PostgreSQL partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html) support conditional uniqueness, but a unique index alone cannot enforce a rule involving status on another table; the open-case guard addresses that separately.

Composite FK examples: `(case_party_id, case_id)` must reference the same case party; a follow-up reply references `(request_id, recipient_party_id, case_id)`; a file's application owner must match its linked party; agenda hearing case must match hearing case; decision disposition must reference a party of the decision's case; decree issuance must reference the approved version of that same decree. Physical design should use concrete checked relationship tables rather than unvalidated `entity_type/entity_id` pairs for business links.

Search initially uses PostgreSQL text search for council-authorized case, person, file metadata and approved extracted text. Apply authorization before result counts, ranking, snippets, exports, and autocomplete. Applicant search is restricted to their own application/materials. Search indexes and materialized reporting views are private and access-controlled. Search should not expose existence through differing errors or constraint messages.

Dashboard metrics are derived: total/new/open cases, duration (filed to closed with stated date boundaries), workload, reason/outcome distribution and session counts. Per-party permission outcomes must not double-count cases. The prototype's 'divorce rate' cannot be calculated from tribunal cases alone without a denominator of all marriages; label case-cohort distributions accurately. 'Raised in Egypt/America' is not inferable from birthplace/nationality; exclude until an approved explicit question and purpose exist. Reports and PDF/CSV/Excel exports require explicit scope and permissions, with CSV formula-injection handling and private expiring outputs.

## 13. Preservation, backup and recovery

Closed cases remain historical evidence. No cascading delete from account deactivation, current profile correction, staff departure, or directory cleanup. Reference catalogs are versioned; outcomes, templates, workflow definitions and declarations referenced by submissions/issuances cannot be deleted or relabeled retrospectively.

Use database backups plus WAL archiving for point-in-time recovery, coordinated private originals/derivatives manifests, separately backed-up encryption keys, and an encrypted off-server recovery copy. Backups on the same server are insufficient for loss of the host. Verify checksums and restore into an isolated recovery environment; test access rules and file links after restore. Store last successful backup and restore-test evidence. Set retention, recovery point and recovery time targets with the operator; they are not established service guarantees.

Use a manifest/watermark to identify file versions committed by each recovery point; restore missing objects from immutable/versioned storage copies and reconcile pending uploads/outbox work. Preserve number allocations that may have been communicated after the recovered DB point before resuming creation, to prevent reissued identifiers. Restore jobs do not send old emails automatically. Recovery procedure includes session/secret revocation when needed.

Confirmed: cases and their full submitted record are retained permanently and never purged. The prototype permanent-purge button is excluded from production. Archival does not authorize deletion; cleanup is restricted to unrelated temporary technical artifacts and must preserve all retained case originals and history. Legal/canonical retention, signature requirements, disclosure authority, and exact confidentiality wording require responsible institutional review; this architecture makes no legal privilege guarantees.

## 17. Implementation acceptance checks

- A cannot read B's draft, submission, file, thumbnail, video range, message, attestation, identifier, search snippet or activity by substituting IDs, copied URLs, alternate endpoints, nested joins or exports; the reverse holds. Shared case membership never changes this.
- Staff authorized to read council cases sees both parties' committed submissions and provenance. Revoked membership/session loses access; role denial covers direct requests and background/export retrieval.
- Simultaneous A submissions create one case for one idempotent request; competing new-case requests for one person yield at most one open case. Adding B to the existing case cannot allocate a new number. Reopening cannot bypass another current case.
- Midnight/timezone, concurrent daily allocation, sequence exhaustion, transaction rollback, restored counters, collisions, duplicate accounts and identity-merge scenarios have deterministic audited behavior.
- Wrong-case/party links fail at database boundary; application ownership cannot be changed by request payload; connection-pool reuse does not retain another actor's RLS context.
- Submitted revision/signature/declaration cannot mutate. Current profile/template/workflow/outcome edits do not change old snapshots or issued PDFs. Conflicting spouse assertions remain attributable.
- Malicious MIME/extension mismatches, oversized files, image bombs, embedded active content, interrupted uploads, worker failure and rejected scans remain unavailable and isolated. Originals survive safe derivative generation.
- Decision deferral remains open; party permission can differ; unauthorized staff cannot issue a decree; closure releases both claims atomically; purge cannot override a hold.
- Outbox retries do not duplicate notifications or PDF issuance; sensitive contents do not leak to email/public inquiry channels/CDN/logs.
- Database, files, encryption keys and identifier allocation are restored together in a recorded recovery exercise before production use.
